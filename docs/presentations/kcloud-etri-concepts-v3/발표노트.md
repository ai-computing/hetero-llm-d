# ETRI 기술 소개 — 본문 10장 + 부록 2장

## 1장

서로 다른 요청과 서로 다른 장비를 연결하는 자원관리 문제가 출발점입니다. 상단과 하단의 세 열은 예시이며 특정 요청 종류가 특정 하드웨어에 항상 대응한다는 뜻이 아닙니다. 가운데 질문은 선택 정책이 필요한 지점을 나타냅니다. 최적 배치 정책 전체를 이미 완성했다고 주장하지 않습니다.

근거: README.md; PD disaggregation_HISTORY.md §§1,6,12

## 2장

이 그림은 논리 구조이며 서버별 물리 토폴로지가 아닙니다. 통합 서빙 계층은 모델 경로와 실행 대상 연결을 담당하고, GPU·NPU·CPU에는 각 엔진이 배포됩니다. 관측 도구는 요청 트래픽 자체를 중계하지 않고 기존 메트릭과 Kubernetes 상태를 수집·연결합니다. 모델 파일 공유 저장소도 구성했습니다. 모든 모델이 항상 실행되거나 동일 모델이 모든 가속기에서 실행된다는 뜻은 아닙니다.

근거: docs/ENVIRONMENT-GUIDE.md; manifests/epp/README.md; lmd-top/README.ko.md

## 3장

실제 구현의 응답은 역방향 또는 streaming으로 반환되지만 여기서는 개념적 순서를 그렸습니다. 실행 위치 선택은 경로 분기와 모델 풀 내 endpoint 선택 등을 포함합니다. 요청마다 자동으로 최적 가속기를 고르는 알고리즘이 완료됐다는 뜻은 아닙니다. 다음 장부터 구축·개발한 영역을 강조합니다.

근거: manifests/epp/README.md; PD disaggregation_HISTORY.md §6.1

## 4장

기존 Kubernetes/llm-d/벤더 엔진은 기반으로 활용했습니다. lmd-top과 EPP 점수 관측 확장은 직접 개발했고, 다른 서버에서 자체 KV 소유·이송 런타임과 PD 실험을 수행했습니다. 세 작업이 완전한 자동 제어 루프로 통합되었다고 설명하지 않습니다.

근거: README.md; lmd-top/CHANGELOG.md; PD disaggregation_HISTORY.md §§4–8

## 5장

모델 준비에는 NPU용 사전 컴파일이 포함됩니다. 모든 모델을 모든 장비에 그대로 이식하는 시스템은 아니며 엔진·모델·컴파일 지원 조건을 따릅니다. 공유 모델 스토어와 inventory discovery를 구현했고 lmd-top의 모델 다운로드/컴파일/배포 흐름과 연결했습니다. 구현 이름: Kubernetes, llm-d, model-store PVC, compile Job.

근거: manifests/README-model-store.md; lmd-top/README.ko.md; lmd-top/CHANGELOG.md v0.35.0

## 6장

시연할 때 화면의 모든 열과 단축키를 설명하지 않습니다. 먼저 어떤 모델이 어디서 실행되는지 질문하고, Serving 화면의 상태/실행 노드를 보여준 뒤 Infra의 장비 상태로 이어갑니다. 이 녹화는 전체 UI를 순환하는 기존 데모이며 현재 live 트래픽 녹화가 아닙니다. 실제 구성 스냅샷을 바탕으로 --cast가 사용률과 성능 수치를 합성했습니다. 화면 숫자를 실측 성능으로 설명하지 않습니다. 원본 GIF는 25.14초 157프레임 무한 반복. lmd-top은 상태 조회와 모드별 운영 액션을 제공하지만 자동 최적화 정책 엔진은 아닙니다.

근거: lmd-top/README.ko.md; lmd-top/src/cast.rs; docs/images/lmd-top-ppt.gif

## 7장

LLM 추론의 prefill/decode를 역할로 먼저 설명하고 명칭은 아래에 보조 표기합니다. KV cache는 앞서 계산한 문맥 상태이며 완성된 답변 파일이 아닙니다. 실제 첫 토큰 경계 등의 세부는 생략한 개념도입니다. 이 설명에서 특정 벤더가 항상 입력 처리 또는 답변 생성에 유리하다고 단정하지 않습니다.

근거: PD disaggregation_HISTORY.md §§1,4,6

## 8장

사용자가 제공한 다른 서버의 PD disaggregation_HISTORY.md를 근거로 작성했습니다. 자체 런타임이 KV를 명시적 입출력으로 소유하고, prefill이 만든 KV를 decode에 전달합니다. 초기 재프리필 모사나 prefix-cache 상한 실험과 구분합니다. RNGD→RNGD, RNGD→ATOM, ATOM→RNGD, ATOM→ATOM 네 조합의 기록이 있습니다. 가속기 A/B는 물리 카드 역할이며 별도 서버 간 네트워크 전송을 주장하는 그림이 아닙니다. 현재 서빙 이송 경로는 공유 메모리이고 별도 TCP 커넥터 검증 기록도 있습니다. NIXL/장치 직접 전송은 미완료. 출력 정합 검증 및 llm-d 게이트웨이 배포·측정 기록은 있으나 이번 PPT 제작에서 원격 원시 결과나 추론을 재검증하지 않았습니다.

근거: PD disaggregation_HISTORY.md §§4,6.1–6.3,12

## 9장

이 장은 정량 성과 자랑이 아니라 수행한 비교에서 생긴 자원관리 질문을 설명합니다. 동일 배치 대조군에서 PD 전체 처리량이 높더라도 카드당 효율은 solo가 높았던 조건이 있습니다. continuous batching은 구현했지만 당시 static보다 느렸고 KV 재구성과 호스트 왕복이 원인이었습니다. 후속 스트리밍/프리패치 최적화는 특정 조건에서 지연을 줄였습니다. 단계별 실험은 설정과 버전이 달라 수치를 합산하지 않습니다. 모든 환경에 적용되는 순위나 일반 성능 결론은 아닙니다.

근거: PD disaggregation_HISTORY.md §§6.4,6.5,7,11

## 10장

협업 후보이며 이미 구현한 자동 정책이나 합의된 역할 분담을 뜻하지 않습니다. ETRI는 이종 서빙 구성, 관측·운영 도구, 실제 KV 이송 실험 런타임과 벤치 자료를 기반으로 논의할 수 있습니다. 교수님의 전문 분야에 따라 요청 배치, 단계 분리 기준, 배치 스케줄링, 지연 목표 기반 제어 중 우선 범위를 정합니다. 첫 공동 실험은 모델·버전·입출력·배치·카드 수를 맞추고 latency/throughput/card-efficiency/energy를 비교하는 것으로 제안합니다. 운영 상태와 최신 통합 스윕은 후속 확인 필요합니다.

근거: lmd-top/README.ko.md; PD disaggregation_HISTORY.md §§11,12

## 11장

본문에서는 개념을 먼저 설명하고 이 표에서만 구현 명칭을 연결합니다. 기존 기술과 자체 개발을 구별합니다. 모든 벤더 엔진을 수정한 것이 아니라 특정 실험 런타임을 직접 구현했습니다.

근거: README.md; lmd-top/README.ko.md; PD disaggregation_HISTORY.md
