## Slide 1: 이종 자원 관리, 우리는 어디를 개발했나

먼저 저희가 작업한 범위를 전체 계층에서 말씀드리겠습니다. 아래에는 NVIDIA GPU와 Furiosa, Rebellions NPU가 있고, 그 위에 벤더 컴파일러와 실행 엔진이 있습니다. Kubernetes와 Prometheus는 배포와 관측에 활용한 기반입니다. 이 하드웨어나 기반 소프트웨어 자체를 저희가 개발한 것은 아닙니다.

저희가 집중한 부분은 파란 영역입니다. 실행 내부를 분석하고 커스텀 코드와 KV 전송 경로를 구성한 일, 그리고 모델 준비와 배포·관측을 연결하는 lmd-top을 만든 일이 있습니다. 그림의 위아래 관계는 작업 계층을 뜻합니다. 모든 구현이 하나의 자동 제어기로 통합됐다는 의미는 아닙니다.

이 작업들을 묶는 질문은 같습니다. 어떤 모델을 어떤 조건으로 준비해서 어느 자원에 실행해야 하는가입니다. 먼저 왜 장비 선택만으로는 충분하지 않았는지 말씀드리겠습니다.

## Slide 2: 장비뿐 아니라 실행 조건도 선택해야 합니다

저희가 사용한 NPU 경로에서는 같은 모델이라도 입력 길이와 배치, 병렬성 조건에 따라 준비할 실행 아티팩트가 달라졌습니다. 따라서 모델 파일을 받아서 어느 카드에 올릴지만 결정하는 것으로는 문제가 끝나지 않았습니다.

실제로 Prefill과 Decode bucket, 병렬성, 동시 요청 조건을 바꾸며 실행 특성을 비교했습니다. 성능뿐 아니라 컴파일에 걸리는 시간과 파일 크기, 입력 조건이 맞지 않을 때의 padding 비용도 살폈습니다. 여기서는 GPU와 NPU의 일반적인 우열보다 저희가 사용한 환경에서 관리해야 했던 조건을 강조하고 싶습니다.

결국 배치 정책에는 장비와 함께 실행 조건과 준비 비용도 들어가야 합니다. 그러려면 그 설정이 실제 실행 내부에서 무엇을 바꾸는지 알아야 했습니다.

## Slide 3: 실행을 바꾸기 위해 내부 계층을 분석했습니다

그래서 컴파일과 런타임 내부에서 사용자가 개입할 수 있는 지점을 나누어 조사했습니다. 가장 위에서는 DSL이나 모듈 단위로 연산을 구성할 수 있고, 더 내려가면 Rust LIR에서 연산 매핑과 메모리 이동을 다룹니다. 마지막으로 생성된 바이너리가 아티팩트에 묶여 실행 엔진으로 연결됩니다.

가운데 메모리 경로는 저수준에서 무엇을 살폈는지 보여줍니다. HBM과 DM 사이에서 데이터가 어떻게 이동하고, 연산과 DMA가 어떻게 연결되는지가 주요 관심사였습니다. 저희가 벤더 컴파일러 전체를 새로 개발했다는 뜻이 아니라, 제공된 계층과 도구를 분석하고 커스텀 실행에 필요한 경로를 확인했다는 의미입니다.

이 분석이 유용하려면 실제로 우리 코드를 실행 흐름에 넣을 수 있어야 합니다. 다음은 그 연결을 위해 만든 도구입니다.

## Slide 4: 기존 엔진에 우리 실행 코드를 연결했습니다

그림 위쪽은 기존 아티팩트의 실행 단계들이고, 아래쪽은 그중 일부만 우리 코드로 바꾼 모습입니다. 전체 엔진을 다시 쓰는 대신 필요한 stage를 교체할 수 있도록 L8Swapper를 구현했습니다.

교체할 코드는 기존 stage와 입력·출력 규격이 맞아야 합니다. 이를 확인하고 컴파일 결과를 교체·저장한 뒤, 기존 엔진에서 해당 바이너리가 호출되는 경로를 검증했습니다. 제공된 기록에는 tokenwise stage 교체와 Rust 바이너리의 런타임 dispatch 확인이 있습니다. 특히 passthrough dispatch 검증을 완전한 attention 알고리즘 교체 검증으로 확대해서 말하지는 않겠습니다.

핵심은 실행의 일부를 바꿔볼 수 있는 수단을 확보했다는 것입니다. 여기서 한 걸음 더 나아가, 실행 단계를 서로 다른 장비에 맡기는 방향도 시도했습니다.

## Slide 5: 실제 KV를 넘겨 NPU 사이에서 실행을 나눴습니다

입력 문맥을 처리하는 Prefill과 이후 토큰을 생성하는 Decode를 분리했습니다. 중요한 부분은 가운데 KV cache입니다. 프롬프트를 다시 계산하는 모사가 아니라, Prefill이 만든 KV를 전달받아 Decode가 실행을 이어가는 경로를 구성했습니다.

이를 위해 직접 KV를 소유하고 입출력으로 다루는 런타임과 커넥터를 구현했습니다. 별도 개발 서버의 작업 기록에서는 Furiosa RNGD와 Rebellions ATOM의 동종·이종 조합, 그리고 Prefill과 Decode 역할 교환을 확인했습니다. 공유 메모리 기반 서빙과 별도의 TCP 전송 검증 기록이 있으며, 과거 자료의 GPU–NPU 분리 가능성 검토와는 구분합니다.

분리 자체가 항상 빠른 것은 아닙니다. KV를 장치에 유지하는 방식, 연산을 어디에 둘지, 컴파일할 그래프와 shape 조건을 바꾸면서 비용을 분석했습니다. 이제 이런 실행 환경에서 모델을 어떻게 준비하고 운영하는지 상위 계층으로 돌아가 보겠습니다.

## Slide 6: 준비와 운영을 lmd-top에서 연결했습니다

lmd-top은 이종 환경에서 모델의 준비와 운영 상태를 연결하기 위해 개발한 도구입니다. 원본 모델과 컴파일된 산출물을 구분하고, 벤더 컴파일 Job과 배포 작업을 관리하며, 모델·요청·장비 상태를 같은 도구에서 확인합니다.

오른쪽은 실제 observe 모드 터미널 출력을 색상까지 보존해 녹화한 화면입니다. 위쪽에는 모델과 빌드 목록이, 아래쪽에는 작업 진행이나 실패 상태가 보입니다. 화면의 값은 캡처 당시의 상태이며 성능 비교 결과가 아닙니다. 컴파일러 자체를 lmd-top으로 만든 것이 아니라 벤더 도구를 실행하는 작업을 관리합니다.

앞에서 설명한 PD 런타임과 lmd-top은 각각의 연구·구현입니다. 완성된 자동 PD 제어기로 통합했다고 보시면 안 됩니다. 다만 실행을 바꿀 수 있는 기반과 상태를 관측·운영하는 기반이 있다는 점에서, 다음의 정책 연구와 연결할 수 있습니다.

## Slide 7: 다음은 조건·단계·장비를 함께 고르는 정책입니다

처음의 전체 지도로 돌아오면 저희가 확보한 기반은 세 가지로 정리됩니다. 실행 조건과 내부 비용을 분석한 자료, 커스텀 코드나 단계 분리를 실행해볼 수 있는 경로, 그리고 모델 준비와 상태를 연결하는 운영 도구입니다.

이 기반 위에서 함께 연구하고 싶은 질문은 언제 실행을 나누는 것이 유리한지, 어떤 컴파일 설정과 장비 조합을 선택해야 하는지입니다. 예를 들어 컴파일 비용과 실행 성능을 예측하거나, KV 이동 비용까지 포함한 단계 배치 정책을 평가하는 방식으로 역할을 나눌 수 있습니다.

여기서 오른쪽은 이미 완료한 자동 최적화 기능이 아니라 공동연구 제안입니다. 저희가 확보한 실행·관리 기반과 다른 연구진의 비용 모델이나 정책을 연결해, 실제 환경에서 비교할 수 있는 접점을 찾고자 합니다.
