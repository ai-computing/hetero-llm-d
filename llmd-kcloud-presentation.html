PART 1 · 왜 llm-d인가

LLM 서빙은 일반 웹 트래픽처럼 분산하면 망가진다

LLM 요청은 느리고, 비용이 요청마다 제각각이고, GPU 메모리(KV 캐시)에 상태가 남는다. 그래서 라운드로빈·least-connection 같은 표준 로드밸런싱은 가속기 포화도·큐 적체·어느 pod가 이 대화를 캐시하고 있는지를 전혀 모른 채 아무 데나 보낸다 → GPU 낭비 + 지연 폭증.

PART 1 · 정의

llm-d = vLLM 위에 얹는, Kubernetes-native 분산 추론 오케스트레이션

모델을 실제로 돌리는 것은 vLLM(추론 엔진). llm-d는 그 위에서 "요청을 어느 pod로 보낼지 · 어떻게 스케일할지 · prefill/decode를 어떻게 나눌지"를 관장하는 오케스트레이션·라우팅 계층이다. 슬로건은 "any model, any accelerator, any cloud".

배경

2025.05 공개

Red Hat 주도 + CoreWeave · Google · IBM · NVIDIA 창립 기여. 2026.03 CNCF Sandbox 편입.

기반

vLLM + K8s + GIE

추론 엔진 vLLM, 오케스트레이션 K8s, 라우팅은 Gateway API Inference Extension의 대표 구현체.

핵심 가치

추론 인지 라우팅

GPU 개수가 아니라 KV 캐시·큐·부하를 보고 최적 pod를 고른다 — 이게 표준 LB와의 차이.

PART 1 · 먼저 알아야 할 3개념

추론은 두 단계로 나뉜다 — 이게 모든 설계의 근거

① Prefill · 프롬프트 읽기

입력 프롬프트 전체를 한 번에 처리해 KV 캐시를 생성. 연산량이 많은 compute-bound. 여기서 걸리는 시간이 곧 TTFT(첫 토큰까지).

② Decode · 토큰 생성

토큰을 하나씩 순차 생성하며 KV 캐시를 재사용. 메모리 대역폭에 묶인 memory-bound. 토큰 간 간격(ITL)이 스트리밍 체감 속도.

③ KV Cache

이미 처리한 토큰의 key/value를 저장해 decode가 다시 계산하지 않게 하는 GPU 메모리. 같은 프롬프트 앞부분(prefix)을 공유하면 재사용 가능 → llm-d가 "이 캐시를 가진 pod로 보내자"고 라우팅하는 이유.

PART 1 · llm-d가 특별한 이유

세 가지 핵심 최적화

① KV-cache-aware 라우팅

캐시를 가진 pod로

프롬프트 prefix의 KV 캐시를 이미 가진 pod로 보내 재계산 회피.

벤치마크: TTFT P90 ~31s → 0.54s (~57×)

② Prefill / Decode 분리

단계별 독립 스케일

compute-bound prefill과 memory-bound decode를 별도 인스턴스로 분리해 각각 최적 HW·병렬화.

KV는 NIXL(RDMA)로 prefill→decode 전송. 처리량이 아니라 지연(tail) 제어가 목적.

③ Workload 오토스케일

변형별 최적 replica

같은 모델의 다른 HW·설정("variant")을 Prometheus 신호로 최적 replica 산정.

HPA/KEDA를 대체하지 않고 목표치를 던져 구동 — 저렴한 variant 우선 확장.

PART 3 · GPU vs NPU · 차이의 근원

PART 3 · GPU 우위

GPU만 되는 것 — 그리고 NPU 우회책

Multi-LoRA (동적 swap)

가중치가 정적 컴파일 → 런타임 어댑터 swap 불가.

우회 → LoRA를 base에 fuse 후 재컴파일, 어댑터당 별도 Pool (메모리 N배)

Speculative decoding

draft·target 두 그래프를 한 loop에서 교차 실행 필요 → 고정 그래프와 충돌.

우회 → 별도 draft 컴파일 + custom pipeline (SDK 기여 수준)

런타임 Quantization

AWQ/GPTQ/FP8 dequant 커널을 GPU에서 동적 실행.

우회 → RBLN rbln_w4a16 컴파일 / Furiosa INT4 artifact 교체

임의 모델 즉시 서빙

새 아키텍처를 런타임 로드.

우회 → SDK 컴파일러 지원 매트릭스 안이어야 하고, 컴파일 단계(≈1시간) 필요

PART 3 · NPU 우위

NPU가 강한 것 — 표준 서빙은 거의 다 커버

Rebellions

압도적 전력효율

~30W/장 × 4 ≈ 120W로 8B 서빙. perf/watt 우위 + KONI 한국어 fine-tune.

Furiosa

Long context 131k

HBM 64GB/장. max 131,072 즉시. RAG · 장문 요약에 유리.

공통

표준 서빙 풀커버

chat · streaming · JSON · prefix caching · TP · 메트릭 → KEDA · EPP 라우팅 · SLO 전부 실측 통과.

한 줄 결론 — NPU는 표준 LLM 서빙을 거의 다 커버하고, GPU가 확실히 우위인 건 LoRA · speculative · 런타임 quantization · (Furiosa 한정) tool calling 뿐. 그 차이는 전부 "컴파일 vs 런타임"이다.

PART 4 · K-Cloud 자원관리

문제 정의 — 이종 가속기를 어떻게 관리할 것인가

국산 NPU(Rebellions · Furiosa)를 포함한 이종 가속기 풀을 한 클러스터에서 효율적 · 공정하게 · SLO를 지키며 관리하는 것이 K-Cloud 자원관리의 핵심 난제다. 이 클러스터는 그 난제를 실제 하드웨어 위에서 실증할 수 있는 드문 환경이다.

CONCLUSION

vendor-neutral 게이트웨이 + 이종 자원관리 = K-Cloud 실증 기반

Takeaway 1

llm-d는 vLLM 위의 추론 인지 라우팅 계층 — GPU·NPU·CPU를 한 IP 뒤에서 동시 서빙 중.

Takeaway 2

GPU/NPU 차이는 전부 컴파일 vs 런타임. 표준 서빙은 NPU도 커버, 유연성만 GPU 우위.

Takeaway 3

그 차이 자체가 자원관리 연구의 대상 — 배치·라우팅·컴파일·disagg·공정분배·관측.

이 플랫폼은 vendor-neutral OpenAI 호환 LLM 게이트웨이다. 사용자는 한 IP만 알면 되고, 운영자는 InferencePool · InferenceObjective · ResourceQuota 세 객체로 정책을 표현한다 — K-Cloud 자원관리 연구를 실제 하드웨어 위에서 검증할 토대.
